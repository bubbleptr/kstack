# 前端口味草图

> 状态：草图，待挑战。依据是 nmem 里的 UI 记忆（约 2026-04 到 2026-10）和 PiGUI 的设计系统文档。每条后面标了出处，方便核对。没有证据的地方不硬编，统一列在第 4 节。

## 1. 从证据里读出的口味

### 1.1 审美是整体效果，先做减法

- 你的原话是「审美是整体效果」，做的是减法，而不是增加熵（06-25）。AI 学得会规律，学不会品味：默认产出「视觉过度安全、结构没有叙事」。
- 删除的例子很一致：
  - hero 主按钮和另外三个入口重复，删了（06-13）；
  - 对话框只留一个关闭按钮（07-20）；
  - Dock 表头在 rail 图标和 tooltip 已经命名过之后，算「第三遍」，删了（PiGUI #184）；
  - 心跳动画全局只出现一处，因为「两处心跳等于两个主语」；
  - 外观页内容太少，就并进通用页，不为未来的功能预留复杂度（05-28）。
- **规则**：同一个信息只说一次，同一个主语只有一个表现。每加一个元素，先问删掉它会坏什么。

### 1.2 诚实态：不伪造数据，不假装知道

这是你最独特的一条，也是模型最不会主动做的：

- 计时没有锚点就不显示数字，因为写「0.0s」等于宣称 run 刚开始。
- 拿不到压缩阈值就不画刻度线：「画一条猜出来的线比不画更误导」。
- 估算的时长段用斜纹加弱化标出，不伪装成实测。
- 上下文用量还没上报时，只画空轨道，不画假弧线。
- 模型列表清空就表示全部隐藏，不悄悄回退成全显（09-22）。
- 空账本不能显示成 $0（后端组已收）。
- **规则**：每个数字、进度和状态都要回答「这是实测、估算还是未知」。未知就显示为未知，估算要看得出是估算。

### 1.3 参照驱动，而不是从文字概念出发

- 三个 AI 生成的落地页方向你都说「都不好看」，于是改成从好的现成网站出发（06-04）。
- 实际引用过的参照：
  - 网站和产品：typeless.com、openless.top、Modal、Lovable（只取布局）、Readwise、Caicai 的博客、Liveblocks、Lassie、Parallel；
  - 图标：Codex 的工具图标；
  - 版式和文档结构：kami、Fumadocs 的盒模型。
- 组件形态靠原型对比来选：PiGUI 里有大量「原型探索 X 胜出」的记录（model selector、composer、dock 形态等）。
- **规则**：方向未定时，先找 2 到 3 个真实参照，或者做几个能实时切换的原型让你挑，不要写一段设计概念让你想象。

### 1.4 跟库走，自建要有理由

- 每个项目选一个组件库，叠一层薄壳，优先用库的默认值（HeroUI Pro，06-24）。
- 先在库里找，找不到再自建。自建组件要放进 `shared/ui`，同一个 PR 登记到 `/design` 画廊，并在总表里写明为什么自建（PiGUI 硬规则 1）。
- 换库之后不留旧库的残余（HeroUI 残余审计，09-05）。
- 样式只写 token，不写字面量；不引入新的样式方案（08-11）。

### 1.5 视觉细节（有证据的）

- **图标**：只用一套成熟图标库（Hugeicons，允许个别明确的例外），16px、线宽 1.5。菜单里用 24px「显大、显丑」。不要自己画图标，也不要 emoji。
- **字体**：
  - 字重只用 400、600、700 三档；
  - UI 文字不小于 12px；
  - 变化的数字一律用 `tabular-nums`；
  - 聊天里的标题比正文大一档，其余标题不小于正文。
- **颜色**：颜色承载语义。「不可用」用灰色，不用橙色，因为橙色读起来像警告（06-07）。图形分类色和文字状态色分成两族，不互相借用。品牌色只出现在品牌在场的地方。
- **背景与插画**：要纯白或冷灰配蓝图式线稿。暗色 3D 光流嫌丑，暖纸色嫌「黄不拉几」（08-14）。
- **布局**：
  - 不要 bento 那种有明显边界的分块（06-12）；
  - 层级和语义要对，「总不可能都是 best」；
  - 一屏只有一个 primary 按钮。
- **间距与表面**：
  - 输入区底部 8px 太挤，改成 12px（06-28）；
  - composer 去掉边框和内阴影，只保留一层恒定的浅外阴影（09-13）。
- **行操作**：「…」菜单常显，不只在悬停时出现（08-31）。

### 1.6 动效：克制、纯 CSS、可减弱

- 不引入 Motion 库。没有手势驱动的交互时，用纯 CSS transition 就够了，而且可以中断（09-05）。
- 每个动画都要有 `prefers-reduced-motion` 分支。静止状态下不写 `transform` 和 `will-change`，因为踩过 stacking context 导致点击失效的坑。
- 图标动效一轮 800ms，只在指针移入时播一次，按下不缩放（09-26）。
- 你在实验里否定过轮播和倾斜预览（06-13）。

### 1.7 文案

- 直白的中文，例如「查不到这个工具现在的定义…」（08-19）。

### 1.8 过程偏好

- 实现前先对齐设计意图：「先讨论，不要着急写」（08-31、09-14）。
- UI 工作留在主循环里做，不派给 coder 子代理（08-31）。
- UI 改动默认截图给你看（07-25）。只看截图不够，页面是否真能访问到也要检查（09-09）。
- 你不喜欢弹窗式提问（10-17），待定问题直接写在文字里。

## 2. emil 的内容怎么处理

| 处理 | 内容 |
|---|---|
| **升格为正文** | 你明确认可或纠正过的：减法、不要 indigo 和 emoji、tabular-nums、减动效、一屏一个 primary |
| **降级到 `references/`** | 精确数值和查表：缓动曲线、时长档位、OKLCH 色阶、字号阶梯、44px 触控目标、iOS 输入框 16px |

| **不收** | marketing-pages、product-thinking、get-creative、design-vocabulary：与主线无关，或者已经被「参照驱动」取代 |

## 4. 待定问题

1. **统一风格，还是按产品换调性？** 你的产品有 Dense Glass、Quiet、Ma（单一竹绿强调色）、Modal 式磷光终端等不同调性。我的提议是：`ui-taste` 只写跨产品不变的部分，即减法、诚实态、视觉细节和动效纪律；每个产品的调性写在该项目自己的 DESIGN 文档里。
2. **产品 UI 的标杆是谁？** 落地页有很多参照，但应用界面（桌面端、控制台）几乎没有。Linear、Raycast、Codex、Claude、Things、Apple HIG 在 nmem 里都没有证据。如果有你认同或明确讨厌的，请点名。
3. **前端组是否覆盖原生？** 你正从 React Native 转向 SwiftUI + Rust 核心（10-16），nmem 里也有不少 SwiftUI 的坑。我的提议是：前端组先只管 Web 和 Electron；SwiftUI 以后单独做 `apple-native`，不混进来。
